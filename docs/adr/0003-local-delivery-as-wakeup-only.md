# ADR 0003: 就近消费仅作唤醒信号

- 状态：已接受
- 日期：2026-11-11

## 背景

同进程发布事件后，若只靠周期 poll，投递延迟等于轮询间隔。希望同进程场景
"发布即处理"，但又不能为低延迟引入第二套投递语义。

## 决策

- 同进程直投只是**唤醒信号**：内存 channel 触发本实例 poller 立即拉取/
  认领，不是投递本身。
- 读取与认领**仍走后端存储**，与周期 poll 完全同路径。
- 跨实例与直投失败（channel 满、本实例无对应订阅、进程重启丢信号）由周期
  poll 兜底，不保证信号必达。
- **绝不引入"本地直投跳过存储"的快路径**。

## 理由

- 信号路径与 poll 路径合一，投递语义只有一套：所有认领、重试、水位
  语义在快慢两条触发路径下行为一致。
- "跳过存储"的快路径会造成语义分裂：本地消息不经后端，则认领互斥、崩溃
  重投、完成状态查询、事件保留窗口全部失效，等于两种不同质量的事件系统。

## 备选

- **本地直投跳过存储**（发布时同进程 handler 直接调用）：延迟最低，但语义
  分裂，否决。
- **不做就近唤醒**：实现最简，但同进程场景延迟受轮询间隔支配，与"低频事件
  但希望及时处理"的定位不符。

## 后果

- 就近唤醒的正确性不承载任何投递保证，最坏情况退化为周期 poll 延迟。
- 需求驱动的定向路由（哪个订阅声明了哪个类型）由订阅注册表提供，见
  [ADR 0004](0004-demand-driven-pull.md)。

# ADR 0004: 需求驱动的拉取

- 状态：已接受
- 日期：2026-11-11

## 背景

消费端只关心自己订阅的事件类型。若拉取在存储侧不做过滤，会把无法处理的行
反复捞出；若过滤发生在取回之后，既浪费读取，更会破坏跨实例认领语义（把别
人能处理的行先抢到手再丢弃）。同时需要回答：唤醒信号路由给谁、事件分发给
谁、已读水位如何维护。

## 决策

**订阅注册表（订阅 → 事件类型集；认领订阅绑定消费者身份）是需求的单一事实
源**，承担三重职责：

1. **条件下推**：把"我要什么"编译成查询条件（类型集 + 租约过期判据 + 可认领/
   水位条件）下推到后端，在单条认领/读取操作内完成；广播消费的已读水位由
   core 内存维护并随 Fetch 传入，不在存储侧簿记。
2. **定向路由**：就近唤醒信号按注册表路由到本实例对应订阅的 poller。
3. **分发**：取回的事件按注册表分发给对应订阅的 handler。

配套规则：

- **过滤必须发生在认领/读取时**，而非取回之后。
- 广播消费的已读水位按订阅类型在 core 内存中维护，**只进不退**（单调守卫），
  以支撑按类型轮询；不在存储侧簿记。
- **按类型轮询限额取数**：单类型洪泛会饿死其他类型，编排每轮对
  各类型限额取数。
- **通配订阅（消费全量）基线不允许**，订阅必须显式列出类型。

## 理由

- 原子下推是认领语义的根基：过滤与认领分离会出现"抢到不处理"的窗口，行被
  一实例空转占住租约，或广播消费水位被无关行推进。
- 水位单调守卫使按类型轮询在多类型并行拉取时互不干扰；认领消费的进度由
  认领簿记自身承载，广播消费不补投，均无需存储侧游标。
- 类型限额是低频事件场景下的简单公平调度，避免引入复杂优先级队列。

## 备选

- **取回后过滤**：实现简单，但空转读取 + 认领语义被破坏，否决。
- **通配订阅**：省去显式类型清单，但使条件下推退化为全表扫描式读取，且
  新增类型自动流入所有通配消费者，行为不可预期；留作扩展能力再评估。

## 后果

- Driver 接口形状被此决策约束：Claim/Fetch 必须接受订阅类型集等条件参数。
- 契约测试需验证：过滤下推原子性、水位单调、类型间不互相饿死。
- 后端不支持条件过滤时必须模拟（如 inmem Driver），能力边界表注明档位，
  见 [ADR 0005](0005-backend-capability-boundary.md)。

# ADR 0012: outbox 事务性入队与广播位置语义重审

- 状态：已接受
- 日期：2026-11-18

## 背景

outbox 事务性入队的要求：业务事务与事件入队原子提交（不需要事务内发布
的场景可跳过），并**必须重审 ADR 0006 的广播位置语义**——position 分配序
与提交可见序在事务内发布下可能乱序，内存水位会越过晚提交的行
（design.md §5.2 已预告「引入业务事务内发布（outbox，P1）时该语义须随
outbox 一并重审」）。

现状回顾：

- 普通 `Publish` 单语句独立提交：`Driver.Append` 在自己的连接上执行
  INSERT，返回即已提交，广播唤醒信号（`LocalWake`，仅加速，ADR 0003）
  在提交后发出。
- 广播消费的已读水位存于实例内存，Fetch 时作为条件下推
  （`position > After`，ADR 0004）；水位只进不退。
- Postgres 上 position 为 bigserial：**分配发生在 INSERT 时，可见性发生在
  提交时**。并发发布下存在理论乱序窗口（早分配的行晚提交）；单语句独立
  提交使该窗口可忽略（ADR 0006）。事务内发布把窗口放大为常态：事务 T1
  分配 position=5 后继续业务写，事务 T2 分配 position=6 并先提交——广播
  实例处理 T2 的行后水位推进到 6，T1 提交后其行
  `position=5 > 6` 不成立，**永久漏广播**。

## 决策

### 1. 事务性入队的承载形态：core 不定义接口，各后端提供 `TransactionalAppender`

- **core 不定义 `TransactionalAppender` 接口**（连 `any` 参数形态也不定义）。
  与 Inspector/Admin 先例对照：Inspector 之所以能在 core 定义可选接口，
  前提是方法签名完全后端无关（全部为 string / time / int）；事务性入队的
  第一个参数是**调用方业务事务的载体**——pgxc 为 `pgx.Tx`、postgrec 为
  `*sql.Tx`，core 接口若用 `any` 承载则丢失全部类型安全与自文档性，调用
  方传错事务类型只能运行时发现。core 的事件契约类型
  （`event.RawEnvelope`）不变，事务性入队复用同一信封。
- 各后端提供具体类型 `TransactionalAppender` 与 `NewTransactionalAppender`
  构造，方法 `AppendTx(ctx, tx <后端事务类型>, e event.RawEnvelope) error`；
  形态与 Admin 同款（ADR 0010）——**可选面、独立构造路径、与 Driver 共享
  连接与命名空间选项、不经运行面类型获得**（经本构造或组合对象 Store 聚
  合，同一内部构造路径）。类型断言探测在此无意义：调用方必须自己持有事务
  才能调用，构造期即确定载体类型。
- 语义（调用方契约）：调用方在自己的业务事务内调用 `AppendTx`，事件
  INSERT 与业务写共享同一事务，随事务原子提交/回滚；**提交与回滚归调用
  方**，库不 begin、不 commit。position 分配沿用现有序：同一事务内按
  INSERT 顺序分配，不承诺跨事务连续性。
- `AppendTx` 入口先按迁移模式处理持久结构（ensure，与 Admin 写路径一致，
  在调用方事务外的池连接上执行）；幂等语义与普通 Append 完全一致（同 ID
  首写为准，不覆盖、不重投，事务内重复 ID 与跨事务重复 ID 同口径）。

### 2. 广播位置语义重审：唤醒信号缺位无碍，水位越过写为广播显式边界

重审把问题拆成两个独立机制，分别定稿：

**（a）就近唤醒信号缺位——无需修复。** 唤醒信号本就只是加速信号，不承载
投递保证，跨实例与信号丢失由周期 poll 兜底（ADR 0003/0004）。事务内发布
不经 `Publisher.Publish`，天然不发信号；提交后的事件由消费方下一个轮询
周期拉取（广播）或认领轮次认领，最坏延迟 = 轮询间隔。库**不在事务内发
信号**（提交前发信号只会让消费者空拉一趟），也**不在提交后补发**（库不
感知提交时机）。

**（b）内存水位越过晚提交行——写为广播消费的显式边界，不做机制修复。**
广播投递语义本就是尽力而为：不承诺 at-least-once、不承诺保序、失败即跳过
（ADR 0006）。水位按 position 严格推进且只进不退，而客户端无法感知其他
事务的未提交 position，任何「缺口感知」都需要为已广播 position 维护簿记。
定稿口径：

- 广播消费下，事务内发布的事件**可能被并发提交的更大 position 越过水位
  而漏投**（对在途广播实例永久不可见；重启实例的基线锚定到当前 head，
  同样不含）。ADR 0006 的「Start 后发布的事件必然可投递」承诺**收窄为
  普通 Publish 路径**（单语句独立提交，理论残余窗口可忽略——Postgres 无
  提交序全局串行化，且幂等 Append 在同 ID 冲突上会等待在途事务
  （含未提交的 outbox 事务），窗口并非绝对为零；实践中可忽略，**非绝对
  保证**）。
- **认领消费不受影响**：Claim 的拾取窗口直接查库（无水位条件），晚提交
  行最迟在下一次认领轮次可见。需要不丢、可重试、可追踪的场景用认领消费
  ——既有口径，本决策不改变。
- 乱序边界写进 design.md §5.2、usage.md 与后端能力边界表，并由
  eventtest 契约用例钉死（乱序构造下广播不再可见、认领可见）。

被否决的修复方案：

- **广播带 position 重排（已广播集合 / 缺口水位）**：为已广播 position
  维护集合或把「已读」簿记下推到存储，破坏广播消费零簿记的核心收益
  （ADR 0006），多实例下簿记语义复杂；本库定位非高并发非实时
  （design.md §1），为低频事件的重排成本不成比例，否决。
- **同事务 NOTIFY**：`pg_notify` 随事务提交才可见（天然提交序），可作
  低延迟唤醒信号——但只解决「信号」，不修复「水位」：消费者收到通知后
  Fetch 条件 `position > After` 仍取不到被越过的行。且推送唤醒属跨实例
  低延迟唤醒能力（pgxc LISTEN/NOTIFY，见 ADR 0013），不在本项范围，否决。

### 3. 观测发射时机：事务性入队不设库侧观测发射点

库侧任何发射点都在**提交前**（提交与回滚归调用方，库不感知提交时机），
而「AppendTx 返回成功」与「事务最终提交」之间可能被回滚打断——提交前
发射的「成功」观测会与回滚后的落库事实（无行）矛盾。既有观测契约都以
「与落库事实一致」为准（`ClaimResult` 计数与落库对账、`AdminReplayEvent`
与重放事实一致，ADR 0008/0011），无法满足即不发射：**事务性 Append 不发
指标、不打日志、不发 Observer 事件**。业务事务的成败本就处于调用方的观
测范围内（业务事务的提交点计量是使用方职责）。

### 4. 惰性清理：事务性入队不在调用方事务内触发

普通 Append 随写机会性触发惰性清理；事务性 `AppendTx` 的清理 DELETE 会
落在**调用方的业务事务内**，扩大其锁面与事务范围。定稿：`AppendTx` 不触
发清理，机会性清理由普通 Append / Claim 等路径照常承担（清理是机会性的，
不依赖单一触发点）。

### 5. position 语义定稿

- 同一事务内多次 `AppendTx` 按 INSERT 顺序分配 position（序内连续）；
  不承诺跨事务连续性（既有契约只承诺 Fetch 严格大于、升序）。
- 回滚的事务不产生事件行；**position 是否被消耗属后端实现细节**——
  Postgres 序列不回收（回滚行留下缺口），inmem 模拟对齐该行为（分配即
  消耗）。消费侧契约（Fetch 严格大于、升序；Claim 无位置连续性假设）不
  依赖连续性，缺口被契约测试钉死可容忍。
- 调用方不得把事务内拿到的任何位置信息当水位使用（`AppendTx` 也不返回
  position）：提交前 position 不对外可见，`HeadPosition` 只锚已提交行
  （基线锚点语义不变，契约测试钉死）。

## 后果

- core 不新增任何接口或类型；本项改动全部落在后端与 eventtest：
  pgxc / postgrec 新增 `TransactionalAppender`（`NewTransactionalAppender`
  构造、`AppendTx` 方法，INSERT 语句与普通 Append 共用同一份定义）、
  Store 增加聚合字段；inmem 新增最小事务模拟（缓冲写入、Commit 原子应
  用、Rollback 丢弃、position 分配即消耗），契约套件无需按后端门控。
- eventtest 新增 `RunTransactionalAppendSuite`：套件经注入的事务适配
  （后端装配 `BeginTx` / `AppendTx` / `Commit` / `Rollback`）不绑定具体
  事务载体，覆盖回滚零事件、事务中途回滚连带先前 Append 一起丢弃（钉住
  「不逐条自治提交」）、提交前对外不可见（隔离性与 HeadPosition）、提交
  后广播/认领可见、事务内幂等、回滚 position 缺口不破坏消费、乱序边界
  （广播漏投 + 认领可见）。
- 使用方按需探测启用：不需要事务内发布的场景可跳过本面（普通 Publish
  语义不变）。outbox 场景的广播订阅者须接受「事务内发布可能漏广播」
  （或改用认领消费）。
- 文档同步：design.md §5.2（乱序边界定稿）与 §6/§9.2（能力面）、api.md
  §3/§4、usage.md（发布语义、广播边界、运维注意事项）、后端 README 能力
  边界表、CHANGELOG。

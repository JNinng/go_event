# ADR 0006: 广播消费发完即忘语义与认领重试退避

- 状态：已接受
- 日期：2026-11-11

## 背景

[ADR 0002](0002-two-consumption-modes-and-lease.md) 确定了两种消费方式的
骨架，但留下三组细节需要定稿：

1. 广播消费的投递与失败语义。
2. 认领消费的"最大处理时长"与心跳续租的精确关系。
3. 失败重试的节奏与上限。

这些语义直接写进契约测试，必须无歧义。

## 决策

### 广播消费：发完即忘

- **无簿记**：消费端不在存储侧留下任何状态（无游标表、无认领记录）；
  消费进度以实例内存中的已读水位记录，由 core 在 Fetch 时作为条件下推
  （见 [ADR 0004](0004-demand-driven-pull.md)），只进不退。
- **起点**：只处理订阅启动后发布的事件；基线在 `Runner.Start` 内同步锚定
  ——对每订阅取 `Driver.HeadPosition`（该类型已提交的最大位置，单条语句
  快照）为初始水位，Start 返回即基线确立，此后发布的事件必然可投递；
  锚点查询失败则 Start 返回错误、整体不启动，可修复后重试。停机与重启
  期间发布的事件不补投，重启从当前位置开始——对齐 Redis Pub/Sub 的
  发完即忘语义。Postgres 上 position 分配序（bigserial）与提交可见序在
  并发发布下存在理论乱序窗口（早分配的行晚提交会被水位越过）；Publish
  保持单语句独立提交使该窗口可忽略，引入业务事务内发布（outbox）时
  须重审本条。
- **失败处理**：handler 失败仅记日志并跳过，不重试、不阻塞、不设死信。
- **投递语义**：尽力而为——不承诺 at-least-once，也不承诺保序（轮询批次
  并发处理下顺序天然不保），均写进契约；需要不丢、可重试、可追踪的场景
  应使用认领消费。
- **实例边界**：广播语义——每个活跃实例各自独立拉取并处理全部事件，实例
  间互不感知、互不影响，实例数不影响语义，无单活跃实例约束。
- **保留窗口**：对本方式仅是存储清理边界，无重投/重放语义。

### 认领消费：租约、心跳与最大处理时长

- 租约 `lease_until` 是唯一有效期判据；认领只针对无主或租约过期行。
- dispatcher 在订阅级**最大处理时长**内自动心跳续租；**超过最大处理时长后
  停止续租**，租约到期后其他实例即可接管。此机制保证挂死（不崩溃但不返回）
  的 handler 不会被无限续保。
- 完成置 `done`：幂等、不可逆。
- **Complete/Fail 以持有租约为前提**：对租约属主做条件更新（CAS 语义）——
  租约过期或已被接管后，旧实例迟到的 Complete/Fail 不生效，不得递增
  `claim_count` 或覆盖新属主的认领状态；否则旧实例的迟到 Fail 会把新属主
  正在成功处理的事件错误推入 `failed`。此竞态与接管场景合并写进契约测试。

### 认领消费：失败重试

- **重试计数以「一次处理尝试未完成」为单位**：显式 Fail 递增 `claim_count`；
  **租约过期被接管（前任未 Fail 而失去租约，含心跳超时停续导致过期）在认领
  时同样递增**——否则每轮都挂死的事件将被无限接管、永不进入终态。接管递增
  与「迟到 Fail 不生效」（CAS）不冲突：迟到 Fail 因失去属主身份而不递增。
- 事件再次可认领时按**递增退避**调度（防热循环：避免失败事件被高频反复
  认领，挤占正常事件的处理能力）。
- `claim_count` 达**重试上限**后置 `failed` 终态，不再被认领。
- 终态之后的处置（手工重放、dead-letter 处理、失败信息留存）归管理面（P1）。
- **惰性清理资格**：超过保留窗口**且无活跃租约**的行（无论终态与否）均可
  被后端清理——保留窗口是重投、重试与完成状态查询语义的硬边界；认领消费
  须将窗口配置为覆盖最坏重试路径（约重试上限 × (最大退避 + 最大处理时长)，
  另留心跳间隔与时钟偏差余量），配置约束写进文档。

## 理由

- 广播消费选择发完即忘而非游标式 at-least-once：通知/广播类副作用本就
  "丢了不致命"，为此维护游标簿记（额外存储结构、多实例交错处理、毒事件
  队头阻塞）成本高于收益；内存水位 + 失败跳过使该方式零存储代价，且天然
  支持多实例广播，无需单活跃实例约束。
- 认领消费的"最大处理时长内才续租"是接管机制的关键：若无条件续租，挂死
  handler 将永久占住事件；若续租窗口太短，慢 handler 会被误接管导致并发
  重复处理。最大处理时长把权衡显式交给订阅级配置。
- 递增退避是防热循环的最小机制：固定间隔在事件持续失败时会形成认领风暴。
- 接管计入重试：租约过期而未 Fail 同样是「尝试未完成」的事实，不计数则
  挂死循环的事件永无终态，违背"失败可观测、重试有上限"。
- 惰性清理以「超窗且无活跃租约」为统一资格：「无活跃租约」保护认领消费的
  在途处理不被误删；广播消费无簿记，清理对其无额外后果，同一规则同时
  覆盖两种方式。

## 备选

- **游标式顺序消费**：按写入序保序 + 游标提交 + 失败原地重试
  队头阻塞 + 单活跃实例约束。保序对通知类场景价值有限，却引入游标簿记、
  多实例限制与毒事件队头阻塞问题，否决。
- **广播消费失败重试 + 死信**：与发完即忘语义矛盾——重试与死信都需要
  簿记状态支撑，需要这些保障的场景应使用认领消费。
- **固定间隔重试**（认领消费）：实现最简，但存在热循环风险，否决。
- **指数退避无上限**（认领消费）：达上限进入 failed 终态是"完成状态可查"
  诉求的一部分，无上限重试使失败不可观测，否决。

## 后果

- eventtest 契约测试范围据此定稿：广播消费（起点语义/失败跳过/广播各自
  全收/水位单调）、认领消费（互斥/接管/接管计入重试/迟到 Complete 与
  Fail 不生效/心跳/超时停续/退避重试/终态）、公共（ID 唯一与幂等 Append
  首写为准、元数据透传）。
- Driver 接口含 `HeadPosition`（广播基线锚点，无事件类型返回空串），
  新后端据此实现基线语义；契约套件以「启动前不补投、Start 后必投递」
  钉死基线（不含时序假设）。
- Postgres 后端无需 consumer_cursor 表：event / event_claim 两表即可，
  存储面收敛。
- 保留窗口是认领消费的硬边界：清理资格为「超窗且无活跃租约」，窗口须配置
  覆盖最坏重试路径；对广播消费仅是存储清理边界。
- 订阅级配置面：最大处理时长、重试上限、退避策略参数（均仅认领消费）；
  广播消费无重试相关配置（签名见 docs/api.md §2.5）。

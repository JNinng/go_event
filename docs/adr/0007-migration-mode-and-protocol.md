# ADR 0007: 迁移模式与迁移协议（幂等语句模型，无台账）

- 状态：已接受（重写，取代 2026-11-16 旧版的结构化 step / 台账协议）
- 日期：2026-11-17

## 背景

持久结构初始化原先只有一条隐含约定：首次使用 Driver 时自动执行幂等 DDL。
该约定在两类场景失效：

1. 运行账号通常只有 DML 权限。以运行连接执行 DDL 会在首次 Append/Claim
   时报权限错误，而调用方无从区分「部署漏建表」与「凭据过期」。
2. schema 需要版本化演进（加列、加索引），需要一个与部署流程兼容、并发
   安全、崩溃可收敛且不引入状态机的迁移协议。

本 ADR 重写旧协议。旧协议描述的是结构化 step、fast/step 双执行路径、
per-step 状态机、owner/epoch 所有权、锁行租约与 `Upgrade` 显式升级模式；
它把迁移做成了一个小型分布式系统。重写后的协议只有一条执行路径：版本
计划 + 幂等语句 + 迁移锁 + 对象集合比对，无台账、无状态机。消费与投递
语义见 [ADR 0002](0002-two-consumption-modes-and-lease.md)、
[ADR 0004](0004-demand-driven-pull.md)、
[ADR 0006](0006-broadcast-fire-and-forget-and-claim-retry.md)；后端能力
分级见 [ADR 0005](0005-backend-capability-boundary.md)。

## 决策

### 1. 迁移模式与向后兼容政策

`MigrateMode` 定义在 core，选项函数由各后端提供：

| 模式 | 语义 |
| --- | --- |
| `Create`（缺省） | 首次使用时持迁移锁幂等应用版本计划全量语句（基线与各版本） |
| `Verify` | 只读校验对象集合与计划期望一致；不执行 DDL |
| `None` | 不建表也不校验，完全交给调用方 |

- 未设置选项即 `Create`，既有调用方行为不变。
- `WithMigrateMode` 只对 `NewDriver` 有意义；显式传给 `Migrate` 返回
  `ErrMigrateModeUnsupported`，避免 `Migrate(..., WithMigrateMode(None))`
  的语义歧义。
- **没有 `Upgrade` 模式**。`Create` 幂等应用计划内全部语句：计划中的语句
  全部幂等且 expand-only（建表/加列/建索引），对旧二进制创建的存量对象
  无害——升级随部署隐式发生，新二进制启动（或显式 `Migrate`）时直接把
  缺失对象补齐，省去版本判定面。expand-only 升级对旧二进制的唯一影响是
  多出的列/索引，旧代码不读取它们。
- `Verify` 覆盖计划全量期望：缺失 → 待升级（处置为执行迁移）；定义冲突
  → 差异报告，只报告、不修复。

### 2. 迁移单元：幂等 DDL 单语句

迁移单元不是裸 SQL 池、也不是结构化 step，而是**版本计划中的幂等单语句**：

- 计划由版本构成：`Version{Number, Statements []string}`；版本号自基线 1
  起严格递增、每版至少一条语句。版本号只存在于计划中，供评审与编排；
  **库内不落版本记录——对象集合即事实**。
- 语句全部幂等且 expand-only：仅建表、加列、建索引（`IF NOT EXISTS`）。
  非幂等 DDL 与数据回填不在机制内。
- **一条语句恰好构造期望对象集合中的一个对象**；计划语句与期望对象按序
  一一对应（该不变量由 postgresschema 单测固定）。
- 约束不在建表语句中内联：`ADD CONSTRAINT` 没有 `IF NOT EXISTS`，统一用
  探测后条件执行的 DO 块创建（仅约束需要；探测使语句可重放）。基线 v1
  的建表语句因此不含内联约束——由旧二进制创建的带内联约束的表在接管
  校验中同样被接受（约束语义一致即可）。
- 后续版本以追加方式进入计划，不修改既有版本语句。

### 3. 执行路径只有一条

```
取锁（有界等待）
  → 接管校验（对象集合与计划期望比对：
        仅缺对象 → 放行执行；
        任一定义冲突 → 差异错误，不修复）
  → 整版单事务依次执行计划内全部语句
  → 提交
```

- 任何失败整体回滚，对象不变；中断后重跑即收敛——幂等语句使「重复执行
  全计划」与「执行缺失部分」等价，不需要逐对象探测、执行状态或恢复矩阵。
- 不做 per-step 状态机、不写执行状态、无 `applying`/`failed` 台账行。
- 中间态可见性：迁移期间 schema 对应用可见。要求停服迁移，或人工保证
  每个版本的语句向后兼容；`Verify` 在启动时报告缺失与定义冲突，运行期
  `None` 模式由调用方承担。
- 失败不持久化：迁移失败直接返回错误；永久配置错误每次执行报同样的错，
  由 Driver 侧 ensure 负缓存（瞬时退避、永久 fail-fast）防止重试风暴。
  台账的 failed 留档由负缓存替代。
- 后端不支持跨语句事务时，同一语义退化为「整版逐条执行」载体（依赖单条
  语句原子性与幂等收敛）；当前两个 Postgres 后端均为事务档，只走单事务
  路径。

### 4. 迁移锁

- 所有 DDL 走同一迁移通道，执行任何 DDL 前先取锁：并发 `IF NOT EXISTS`
  类 DDL 存在元数据竞态（如 Postgres 的 `pg_type` 唯一键冲突），不能依赖
  语句幂等替代锁。基线与升级共用同一锁键与同一份语句定义。
- 事务级 advisory 锁（随提交/回滚释放）；等待有界：try-lock + 退避，
  总上限固定（`LockWaitTimeout`），DDL 自身锁等待由 `lock_timeout` 限定，
  超时映射为瞬时错误 `ErrMigrationLockTimeout`。不得无限等待。
- 锁键含 schema 命名空间（如 `go_event:<schema>`），不同 schema 或应用
  不互相阻塞。
- 锁能力为无（`LockNone`）时 `Create` 返回 `ErrMigrationUnsupported`，
  只能 `Verify`/`None`；DDL 原子性为无（`DDLAtomicNone`）时同样拒绝。
- 不引入 owner/epoch 所有权、锁行租约与续约——锁随事务生命周期存在，
  不存在「持锁者失联」问题（事务结束锁即释放）。

### 5. 基线接管

已有事件表但非本次执行创建的库（旧二进制、手工脚本、其他工具创建），
按对象集合校验（表名、列与类型、约束列、索引列）：

- 已有对象与期望定义一致且仅缺对象 → 补齐（放行执行计划）。
- 任一定义冲突（列类型、约束列、索引定义不符）或无法判定归属 → 返回
  差异错误（`*VerifyError`），不自动修复、不自动 stamp。

判定依据对象级快照（系统目录读取，事务内一致）。不做「先 `Verify` 再
`Migrate`」的前置门：检查与创建无法组成原子操作，原子性由锁 + 整版事务
保证。

### 6. 手工脚本：`SQL` 与 `Statements`

`SQL` 由版本计划派生：以 `BEGIN` 开始，设 `lock_timeout` 并取迁移锁
（锁语句位于全部 DDL 之前），随后依次输出计划内全部语句（基线 + 各版本，
全部幂等），末尾 `COMMIT`。脚本整段可重放（中断重跑收敛），与执行器
共用同一份语句定义，不维护第二份拷贝。

- 用途：部署流程 / DBA 接管 schema（运行账号仅 DML、`Verify`/`None` 模式
  的库）。
- `Statements` 不含锁；手工执行前必须先取锁，并整段执行，不得拆分跳过。
- 导出物不含账号与授权；库不负责账号或授权管理。

### 7. 并发建索引边界

单一执行路径要求整版语句可事务化。`CREATE INDEX CONCURRENTLY` 不能在
事务内执行：若未来某版本需要并发建索引（大表线上加索引），按当时能力
扩展执行器（该版本退出单事务路径、其余语句保持同语义），不在本协议内
预留机制。当前计划全部语句可事务化。

### 8. 权限边界

- `Create` 与显式 `Migrate` 同义：都以调用方连接执行 DDL，需要 DDL 权限。
- 运行期仅 DML 的连接不能自动迁移，只能 `Verify`（另需系统目录读）或
  `None`；表必须由部署期的高权限连接建好（执行 `SQL` 脚本或调用方自己的
  流程）。
- `Verify`/`None` 模式下库代码不得读取计划中可能尚不存在的对象，除非
  调用方已用部署流程保证 schema 与二进制匹配；`Verify` 对缺失对象给出
  明确报告。

### 9. 实现落点

- core：`MigrateMode`、`VerifyReport`/`VerifyIssue`/`VerifyProblem`/
  `VerifyError`、`MigrationCapabilities`、`FaultPoint`（语句边界：
  `after_lock` / `before_statement` / `after_statement` /
  `before_commit`，供契约测试注入）与迁移哨兵。
- `postgresschema` 方言包（无驱动依赖）：版本计划、计划语句与期望对象
  的一一配对、系统目录快照、差异判定、锁键与锁语句、**共享迁移执行器**
  （`Migrate(ctx, MigrationConnector, schema, opts...)`，后端只适配连接
  与错误分类）。
- 两个 Postgres 后端：`Migrate`（委托共享执行器）、`Verify`、`Statements`、
  `SQL`、`Capabilities`、`WithMigrateMode`；`ensure` 按模式分派并做有界
  负缓存（瞬时错误退避、永久错误 fail-fast、`Verify` 成功缓存）。
- `eventtest.RunMigrationSuite` + `eventtest/simmigrate` 模拟 backend
  （语句边界故障注入）；真实 Postgres 集成由 `TEST_POSTGRES_DSN` 门控。
  inmem 显式声明迁移为 no-op。

## 理由

- **幂等语句可替代探测收敛**：语句自带幂等语义后，「跳过已存在对象」
  与「重复执行无害语句」等价，探测谓词、per-step 状态机与恢复矩阵全部
  失去必要性；接管校验保留一次全局比对，用于区分「缺对象」与「定义冲突」。
- **无台账**：台账在幂等模型下的唯一不可替代功能是 failed 留档，可由
  ensure 负缓存替代；台账带来的引导顺序、双写一致性、reset/stamp 管理
  面远超其价值。引入非幂等语句（如数据回填）时再按当时需要的最小形态
  引入。
- **隐式升级**：expand-only 升级对旧二进制无害，`Create` 直接应用全计划
  省去版本判定面（库内版本读取、too_new 处置、`Upgrade` 模式与文档面）。
- **对象集合即事实**：版本号只存在于计划中，避免台账与目录两份事实源
  的漂移；`Verify` 与接管校验用同一套比对。
- **基线接管采用统一判定而非自动修复**，防止库把「同名但定义不同」的
  对象误认为自己的基线，造成不可逆的 schema 污染。
- **锁先行、有界等待**解决并发首启与长事务占锁两类现场问题；事务级锁
  随提交/回滚释放，无需所有权跟踪。

## 被否决的备选

- **结构化 step + 探测谓词**（每步声明对象类型/探测方式/可事务化，执行器
  逐步探测收敛）：探测与执行之间存在竞态，探测路径要求每步可探测、可
  验证，能力面与文档成本高；幂等语句使探测不必要，否决。
- **per-step 状态机**（`pending`/`applying`/`applied`/`failed` 台账行 +
  崩溃恢复矩阵）：状态机是为「非幂等 DDL」设计的恢复协议；幂等语句下
  「重跑整版」即是恢复，状态机只会引入双写一致性与人工 reset 面，否决。
- **owner/epoch 所有权与锁行租约**（TTL、续约、过期回收）：会话级长持锁
  才需要租约；事务级锁随事务结束释放，无失联状态，复杂度约为事件核心
  两倍且生产路径不可达，否决。
- **迁移台账（含最小形态）**：见「理由」；failed 留档由负缓存替代，
  引入非幂等语句时再评估。
- **`Upgrade` 显式升级模式**：expand-only 升级对旧二进制无害，隐式升级
  省去版本判定面；若未来出现必须显式编排的破坏性变更（contract 阶段），
  按当时的部署流程处理，不在库内建模，否决。
- **保留单一自动迁移、要求运行账号具备 DDL 权限**：与最小权限部署冲突，
  且无法区分部署漏建表与凭据问题，否决。
- **只提供显式 `Migrate`、取消 Driver 构造期迁移**：破坏既有调用方，且
  多实例首启仍需自行编排；保留 `Create` 缺省更平滑。
- **用 `Verify` 作为 `Migrate` 的前置门**：检查与创建非原子，仍会出现
  并发竞态，否决。

## 后果

- 文档需同时给出能力矩阵与连接权限矩阵；能力矩阵的值以各后端
  `Capabilities()` 为准，权限矩阵覆盖 Create/Verify/None。
- 新后端接入必须实现 `MigrationBackend` 并通过 `RunMigrationSuite`。
- 运行期仅 DML 的部署必须显式选择 `Verify` 或 `None`；缺省 `Create` 在
  该场景下会 fail-fast，这是预期行为而非缺陷。
- 升级 = 部署新二进制 + （自动 `Create` 或手工 `SQL` 脚本）重放全计划；
  不存在独立的升级命令与停服窗口控制，升级语义由「计划语句向后兼容」
  这一部署纪律保证。
- 旧版协议（结构化 step、台账、`Upgrade`）不再实现；引入非幂等语句
  （数据回填、收缩阶段 DDL）时需重新评审本 ADR。

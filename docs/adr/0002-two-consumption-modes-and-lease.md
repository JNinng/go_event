# ADR 0002: 两种消费方式与租约认领

- 状态：已接受
- 日期：2026-11-11

## 背景

长尾副作用异步化存在两类诉求：

- 通知、广播类：上游发布后无需感知谁在消费、消费是否完成，丢了也不致命。
- 任务类（如文档摄取向量化）：需要完成状态追踪、失败自动重试有上限、多实例
  分布式下同类型并发互斥（同一时刻至多一个实例在处理；at-least-once，
  不承诺恰好一次）。

现成库（River、Watermill、asynq）均无法同时满足（见 design.md §2），需要
自建消费模型。

## 决策

提供**两种消费方式**，均与载荷形态（强类型 `Declare[T]` / 无参
`NoPayload`）正交，2×2 组合均合法；同一事件可同时被两种方式的消费者处理：

### 广播消费（发完即忘）

- 消费端不在存储侧留下任何簿记（无游标、无认领）：消费进度以实例内存中的
  已读水位记录，由 core 在 Fetch 时作为条件下推（见
  [ADR 0004](0004-demand-driven-pull.md)）。
- 只处理订阅启动后发布的事件；停机与重启期间发布的事件不补投，重启从当前
  位置开始（对齐 Redis Pub/Sub 的发完即忘语义）。
- 投递尽力而为：handler 失败仅记日志并跳过，不重试、不阻塞；不承诺
  at-least-once 与保序（写进契约）。
- 广播语义：每个活跃实例各自独立拉取并处理全部事件，实例间互不感知、互不
  影响，实例数不影响语义。
- 上游发布时无需感知消费方存在。语义细节见
  [ADR 0006](0006-broadcast-fire-and-forget-and-claim-retry.md)。

### 认领消费

- 以 `event_claim(event_id, consumer_type)` 唯一约束为认领簿记。
- 认领即抢锁：只认领无主或租约过期行（Postgres 后端用
  `FOR UPDATE SKIP LOCKED`，语义由契约测试约束）。
- 租约 `lease_until` 即有效期；dispatcher 在订阅级最大处理时长内自动心跳
  续租；超时停止续租，租约到期由其他实例接管——挂死而未崩溃的 handler 不被
  无限续保。
- 完成置 `done`（幂等、不可逆）；失败递增 `claim_count` 并按递增退避置为
  再次可认领（防热循环），达上限置 `failed` 终态；租约过期被接管同样计入
  重试（见
  [ADR 0006](0006-broadcast-fire-and-forget-and-claim-retry.md)）。
- 一个事件可被 N 种 consumer_type 各消费一次；同类型同一时刻至多一个活跃
  租约（接管后旧实例仍存活时存在并发重复处理，整体为 at-least-once，
  不承诺恰好一次）。
- Complete/Fail 以持有租约为前提（对租约属主做条件更新）：租约过期或已被
  接管后，旧实例迟到的 Complete/Fail 不生效，不污染新属主的认领状态。
- 完成状态上游可查。

### 消费者身份（认领消费）

消费者身份是认领消费的概念，作 claim 键（consumer_type）；广播消费不使用
身份——无簿记、无跨实例状态，每个实例独立全收，订阅仅按事件类型集声明。

- Runner 构造级设默认身份，订阅级可覆盖；一个进程可承载多个身份，各身份
  独立认领、心跳。
- 身份是消费者的事实身份而非可热切换的旋钮：新增或变更身份即新消费者从头
  认领（历史事件重投，仅限后端保留窗口内），不是断点续跑；存量身份的
  重命名迁移归管理面（生产化能力）。
- 两种方式统一约定：订阅在 Runner 启动前注册完毕，启动后动态注册留作扩展。

### 通用底线

- 认领消费为 at-least-once 投递，handler 幂等是消费方责任（写进文档与
  契约测试）；广播消费为发完即忘（尽力而为），不承诺投递。
- **租约互斥不是消费去重**：租约只保证同一时刻至多一个实例在处理，接管后
  同一事件仍可能被处理多次；库不在消费路径做去重簿记（广播消费无簿记，
  event_claim 只做互斥）。推荐以事件 ID 为幂等键（去重表 / upsert /
  天然幂等写法均可）；发布侧的重复 Append 同 ID 幂等成功由后端唯一约束
  兜底，属库的职责，与消费侧幂等是两回事。

## 理由

- 广播消费满足"上游无感 + 实现极简"：零簿记（连游标都没有）、零存储代价，
  失败即跳过，天然支持多实例广播。
- 认领消费以租约表代价换取任务类语义：完成追踪、失败重试上限、多实例
  并发互斥（同类型同一时刻至多一个实例在处理）。心跳 + 最大处理时长解决"挂死消费者无法被接管"这一 River 等
  现成方案的缺口。
- 两方式正交而非互相依赖，避免用单一复杂模型同时拟合两类诉求。

## 备选

- **只做认领消费**：通知类场景被簿记开销与终态管理拖累，且"消费完即无痕"
  的广播语义丢失。
- **只做广播消费 + 消费方自建租约**：即 Watermill 路线，租约语义重复建设，
  抽象收益有限。

## 后果

- 存储需要 event / event_claim 两类结构（Postgres 后端）。
- 广播消费与认领消费的细节决策及 eventtest 契约测试范围在
  [ADR 0006](0006-broadcast-fire-and-forget-and-claim-retry.md) 中定稿。
